[FLAG 02]Der Guest, der Admin sein wollteeasy-medium · ~10-15min

[██░░░] difficulty 2/5 · localstorage · client-side session tampering
Diese Seite simuliert einen Login. Die Zugangsdaten fuer den Test-Account (User admin, Passwort admin) sind absichtlich bekannt. Das Backend (das hier komplett clientseitig laeuft) prueft zusaetzlich die Rolle. Nur Nutzer mit Rolle admin sehen die Flag.

Sie sind eingeloggt als admin, aber Ihre Rolle ist guest. Erhoehen Sie Ihre Privilegien.
[!] Angriffsflaeche
Der Browser speichert die Rolle in localStorage. Alles was der Client speichert, kann der Client aendern. Dieser Grundsatz ist der Ursprung des Satzes "never trust the client".

Tipp 1: DevTools > Tab "Application" (Chrome) oder "Storage" (Firefox). Dort finden Sie unter "Local Storage" die Domain und den Schluessel role.

Tipp 2: Direkt in der Console: localStorage.setItem('role', 'admin'). Danach den "Admin-Panel"-Button erneut klicken.

Denkanstoss: Die Flag wird nicht "aus der Rolle abgeleitet", sie steckt im JavaScript-Code. Ihre Anzeige ist ans role==='admin' geknuepft. In echten Systemen waere die Autorisierung serverseitig, dann funktioniert dieses Tampering natuerlich nicht.

[FLAG 04]Der geerbte Adminhard · ~1-3h

[████░] difficulty 4/5 · prototype pollution · js obfuskation
Diese "Konfigurations-App" nimmt JSON entgegen und merged es rekursiv in ein internes User-Object. Danach wird geprueft, ob der Nutzer isAdmin ist. Nur dann wird eine verschluesselte Nutzlast entschluesselt.

Standardmaessig sind Sie nicht admin. Aber der Merge-Algorithmus ist unsicher. Er kopiert Werte nach __proto__ ohne Pruefung. Damit koennen Sie Object.prototype.isAdmin = true setzen und alle nachfolgenden Objekte "erben" den Wert.
[!] Angriffsflaeche

Tipp 1 :: Prototype Pollution Payload:

{"__proto__": {"isAdmin": true}}

Nach dem Uebernehmen erzeugen Sie einen neuen User (Reset). Dieser neue User erbt isAdmin: true von Object.prototype.

Tipp 2 :: Obfuskation lesen: Der Check nutzt atob() um einen base64-kodierten String zu dekodieren. Das ist keine Verschluesselung, nur Verstecken. Wenn Sie das Snippet in die Console pasten und console.log aufrufen, sehen Sie was gemacht wird.

[FLAG 05]Der sichere HTML-Renderervery hard · ~3-8h

[█████] difficulty 5/5 · dom clobbering · sanitizer bypass · html injection
Dieser "sichere HTML-Renderer" nimmt HTML entgegen, entfernt <script>-Tags und JavaScript-URLs, und rendert dann das Ergebnis. Er ist als "XSS-safe" beworben und ist auf den ersten Blick tatsaechlich resistent gegen naives <script>alert(1)</script>.

Aber im Renderer wird eine globale Konfiguration window.appConfig ausgewertet. Wenn appConfig.unlockFlag auf einen bestimmten Wert gesetzt ist, wird die Flag angezeigt. Diese Variable existiert normal nicht. HTML-Elemente mit id="appConfig" ueberschreiben das JS-Objekt (DOM Clobbering).

Ihr Ziel: HTML einschleusen, das den Sanitizer passiert und appConfig.unlockFlag auf den erwarteten Wert clobbert.
[!] Angriffsflaeche
  • Der Sanitizer f5_sanitize(), schauen Sie sich seine Blacklist an.
  • Der Check appConfig?.unlockFlag?.value === expected.
  • HTML-Formulare erzeugen named-elements die sich wie Objects verhalten.

DOM Clobbering :: Kern-Idee: Wenn eine JS-Variable window.appConfig nicht existiert, sucht der Browser als Fallback nach einem HTML-Element mit id="appConfig". Dieses Element ist dann als globale Variable ansprechbar. Bei <form id="appConfig"> werden zusaetzlich seine <input name="...">-Children als Property-Access nutzbar.

Payload-Skelett:

<form id="appConfig">
  <input name="unlockFlag" value="EXPECTED_VALUE">
</form>

Der Renderer nutzt appConfig.unlockFlag.value, genau die Zugriffskette die durch Form+Input erzeugt wird.

Welcher Wert? Schauen Sie sich im JS-Quelltext die Konstante F5_EXPECTED_HASH an. Der Renderer vergleicht sha256(unlockFlag.value) mit diesem Hash. Sie muessen den Klartext-Wert finden, dessen Hash passt. Der Klartext steht als {{CH2_F5_HIDDEN_VALUE}} in einem HTML-Kommentar im Renderer-Bereich unten. Verstecken auf verschiedene Art trainiert auch Ihr Auge fuers Debuggen.

Reale CVEs: HTML sanitizer bypasses in DOMPurify (mehrere historische), Gmail AMP (2019), verschiedene CMS-Editoren. DOM Clobbering: HackerOne-Reports gegen Gmail, GitHub Pages, Bug in jQuery (globals fallback).
